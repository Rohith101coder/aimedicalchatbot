MEDICAL CHATBOT PROJECT - COMPLETE OVERVIEW
==========================================

Purpose and project summary
---------------------------
This is a Django web application for a medical-question chatbot. It provides
user registration and login, administrator approval/blocking of accounts,
chat sessions with stored message history, and responses generated by a
locally loaded Hugging Face causal language model.

The source code should be treated as a demonstration/prototype, not as a
clinically validated medical system. It does not show clinical safety
validation, medical answer evaluation, or a verified production deployment.

IMPORTANT: WHAT THE CODE ACTUALLY IMPLEMENTS
---------------------------------------------
The surrounding project/folder name refers to "Gamma LLMV2" and comparison
using BERT models. In the application source inspected for this overview:

* The active chatbot model is configured as microsoft/phi-2 by default.
* No Gamma model or Gamma LLM V2 implementation is loaded in the chat flow.
* No BERT model comparison, benchmark, or evaluation pipeline is implemented.
* sentence-transformers/all-mpnet-base-v2 is the default embedding model
  configured in a helper, but that embedding initializer is not called by the
  active chatbot view.
* The supplied Gale Encyclopedia of Medicine PDF and PDF chunking utility are
  not connected to the active chatbot flow. The chat view sends the user's
  text directly to the language model; it does not retrieve PDF passages.

For a resume, describe what is implemented (a Django chatbot using Phi-2 via
Hugging Face Transformers) rather than claiming Gamma/BERT comparison or
retrieval-augmented generation unless those features are added and tested.

Local model details
-------------------
Default text-generation model:
* Hugging Face model ID: microsoft/phi-2
* Override setting: MODEL_NAME environment variable
* Loaded using AutoTokenizer and AutoModelForCausalLM
* Wrapped in a Transformers text-generation pipeline and then a LangChain
  HuggingFacePipeline object
* Inference runs in the Django server process. With a model ID from Hugging
  Face, model files are downloaded/cached locally and inference is performed
  on the selected local device; this is not an external hosted inference API.
* torch.cuda.is_available() selects float16 when CUDA is available and
  float32 otherwise. device_map="auto" allows Transformers/Accelerate to
  place model weights on available hardware.
* Generation settings in the source: max_new_tokens=600, temperature=0.8,
  top_k=50, and do_sample=True.

Default embedding model (configured, not active in chat):
* Hugging Face model ID: sentence-transformers/all-mpnet-base-v2
* Override setting: EMBEDDING_MODEL environment variable
* Loaded through LangChain's HuggingFaceEmbeddings when
  LLMInitializer.initialize_embeddings() is explicitly called.
* The active chatbot view does not call that method, and no vector retrieval
  step is present in the active request path.

No other local LLM or BERT classifier is loaded by the inspected application
chat flow. The environment must have sufficient memory and, for faster
inference, a compatible GPU; CPU inference may be slow.

Functional features
-------------------
1. Registration
   * Collects first name, last name, email, mobile number, password, and
     password confirmation.
   * Checks basic email shape, duplicate email/mobile, 10-digit mobile, and
     matching passwords.
   * Creates a UserProfile with a default waiting status.
   * Uses Django password-hashing/checking APIs in the registration/login
     flow.

2. User authentication and access
   * User login checks credentials and account status.
   * Waiting and blocked accounts are denied access; active accounts can
     proceed.
   * User identity is stored in the Django session.
   * The custom login_required_custom decorator protects the chatbot view.
   * Logout flushes the session.
   * User home records a visit count.

3. Administrator workflow
   * An administrator login page and dashboard are provided.
   * The administrator can view registered accounts, activate, block,
     unblock, or delete them.
   * The current admin authentication is a hard-coded demo check in the view,
     not Django's normal admin-user authentication.

4. Chat and history
   * A logged-in user can create chats, send messages, switch between saved
     chats, view history, and delete chats.
   * User and bot messages are stored in SQLite through the Message model.
   * Chat titles are derived from the opening user message (up to 50
     characters) for chats created by sending the first message.
   * The browser communicates with Django using JSON fetch requests.
   * The chatbot view calls the configured language model with the current
     user message, then stores and returns the generated response.

5. Medical PDF helper (not integrated into chat)
   * users/utility/pdf_processor.py extracts text with PyPDF2, normalizes
     whitespace, and splits text with LangChain's
     RecursiveCharacterTextSplitter.
   * Chunking is configured for 1,000 characters with 200 characters of
     overlap.
   * media/gale_encyclopedia.pdf is present in the project.
   * The helper is not called by the chatbot view; no embeddings index or
     retrieval pipeline is established by this application path.

6. Experimental vector-store test
   * users/utility/test.py contains a Pinecone client/index test, separate
     from the active web-chat request flow.
   * This does not establish a working Pinecone-based retrieval feature in
     the chatbot.

Request and response flow
-------------------------
1. A visitor submits registration details.
2. The new profile starts in waiting status.
3. An administrator activates the account.
4. The user signs in; Django session values identify the user.
5. The user opens the chatbot page. At application startup, the configured
   Phi-2 model is initialized by users/utility/llm_setup.py.
6. The browser posts the message and current chat ID to /chatbot/.
7. Django stores the user message, sends the text to the language model,
   stores the bot response, and returns it as JSON.
8. Chat records and messages are persisted in SQLite and can be revisited
   from the chat-history sidebar.

Setup and local run (development only)
--------------------------------------
1. Use a compatible Python environment. The project notes mention Python
   3.11.3, while Flow of Execution.txt mentions Python 3.10.2; confirm the
   intended interpreter before setup.
2. From the directory containing manage.py, install packages from
   requirment.txt into a virtual environment.
3. Apply database migrations with:
       python manage.py migrate
4. Start the Django development server with:
       python manage.py runserver
5. Open http://127.0.0.1:8000/ in a browser.
6. Register a user, then activate the account through the demo admin flow.

The model is initialized from users/views.py at import/startup time. Starting
the development server can therefore take time and requires the model files
and compatible runtime dependencies to be available.

Project limitations and verification notes
-------------------------------------------
* The exact Python requirement is inconsistent across the included notes.
* The active language-model request is direct text generation; there is no
  evidence of medical-document retrieval or a Gamma/BERT comparison.
* Medical responses are not shown to be clinically validated and should not
  be used as diagnosis or treatment advice.
* The development settings use DEBUG=True, an insecure development secret,
  and empty ALLOWED_HOSTS; these are not production settings.
* The demo administrator authentication is hard-coded and must be replaced
  before deployment.
* The login view currently prints a submitted password in debug output. This
  must be removed and any logs containing real credentials handled securely.
* users/utility/test.py contains a hard-coded external-service credential.
  Do not copy that credential into documentation or share the file publicly;
  revoke/rotate it and load future credentials from environment variables.
* PyPDF2 is imported by the PDF utility but is not listed in the provided
  requirment.txt. The Pinecone test also depends on a Pinecone package that
  is not listed there.
* The user/admin tests files contain only empty Django test scaffolding; no
  meaningful automated feature tests were found in those files.
* The project database and model load were not executed as part of preparing
  this documentation.
